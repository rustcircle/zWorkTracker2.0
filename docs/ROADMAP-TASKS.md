## 1. How to use this file

### The loop, per task

1. Pick the first unticked task whose "Depends" are all ticked (waves inside a milestone can go in any order).
2. Open a new Claude session in the repo root (`/Users/p/Z/ZCode/zWorkTracker`) and paste the task's **Prompt**.
3. The session makes the branch `m<n>/<kk>-<slug>` from `main`, works through the subtasks **in order**, and
   ticks each `- [ ]` in the milestone file as it finishes it. **YOU** subtasks you write yourself, with the session
   as your pair; **CLAUDE** subtasks the session writes.
4. The session runs `scripts/gate.sh` (added by M2.1), commits on the branch and reports in plain language.
   It never pushes and never merges.
5. You check the result with the task's **How to check** (no Rust needed), then merge:
   `git switch main && git merge --no-ff m<n>/<kk>-<slug>`. You push when you want.
6. Tick the task line itself. The milestone ends with its gate task (`M<n>.G`).

Sizes: **S** at most 2 h, **M** at most half a day, **L** at most a day (session time; YOU subtasks can take you
longer, that is fine). A task that runs past 1.5x its size is split (section 6).

### Two kinds of subtask

| Mark | Who writes it | What kind of work |
|---|---|---|
| **YOU** | you, Claude reviews | a pure function in `zwt-ui-logic`, a test, a strings or theme entry, a small `.slint` change, a bridge view with a clear contract |
| **CLAUDE** | the session | unsafe or Windows platform code, the renderer, concurrency in the worker or hub, build and packaging plumbing, large `.slint` screens |

Every YOU subtask names: the signature or test to write, a piece of existing code to imitate (`file:line`), the
Rust concepts it uses with a link key (section 4), and a hint ladder: hint 1, hint 2, then ask Claude.
About a third of the subtasks are YOU in M2, rising to about half later.

### Standard rules (every session follows these; the prompts point here)

- **R1 Branch and commit.** `git switch -c m<n>/<kk>-<slug> main`; one task per branch; commit when the gates
  pass; never push, never merge, never rewrite `main`.
- **R2 Read little.** The task entry, this section, PLAN.md §5 (reactive design) and §8 (gates), and only the 1.x
  files the task names under `reference/z-work-tracker/` (the 1.x app, read-only; never edit it).
- **R3 Words are copied, not written.** Every user-visible text is copied verbatim from the named 1.x file into
  `crates/zwt-app/ui/strings.slint` (a block per task, at the end; `crates/zwt-app/tests/parity_strings.rs` diffs it).
- **R4 Colours come from `Theme`** (`crates/zwt-app/ui/theme.slint`, generated by `scripts/gen_theme.py`; never
  edit it by hand). Fonts: Segoe UI Variable and Cascadia Mono from the system, not bundled.
- **R5 No polling.** A new piece of data gets a topic bit in `crates/zwt-bridge/src/topics.rs`; a test in
  `crates/zwt-bridge/tests/topics.rs` asserts the exact bits a change sets and that an unchanged recompute writes
  nothing. Deadlines (sync, reminders) wait on the worker with `recv_timeout`, never a timer loop.
- **R6 The UI never touches `Service`.** It sends a typed `Command` to the worker (`crates/zwt-bridge/src/worker.rs`);
  the worker answers through the hub.
- **R7 Core edits** only when a task says "core change": a separate commit titled `core: ...`, a new row in
  docs/DEPENDENCIES.md §Local edits, the matching item in docs/CORE_REQUESTS.md marked done, and its workaround
  removed in the same commit.
- **R8 `unsafe`** only in `crates/zwt-win` (M3.3), the one exception PLAN §8 allows.
- **R9 Renderer-neutral.** Never depend on which GPU renderer `crates/zwt-app/src/renderer.rs` picks (Vello or
  FemtoVG on wgpu); UI tests run on the testing backend's software renderer.
- **R10 PARITY.md** is never ticked (that happens at M8). If 2.0 must differ from a row, stop and ask the owner.
- **R11 Tests first** where they can be: write the named test, see it fail, then make it pass. A test that needs
  a real window follows `crates/zwt-app/tests/renderer.rs` and is listed in the report.
- **R12 Report** at the end, in plain language: what changed, how it was verified (gate output), the tests added,
  the PARITY rows it implements, anything the owner must check or decide.

### Standard gates

After M2.1, `scripts/gate.sh` runs them all and prints one PASS or FAIL line each (logs in `target/gate/`):

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo clippy --workspace --all-targets --target x86_64-pc-windows-gnu -- -D warnings
ZWT_1X_DIR=$PWD/reference/z-work-tracker cargo test --workspace
cargo build --release --target x86_64-pc-windows-gnu
# after M2.3: cargo test --manifest-path compat/Cargo.toml   (the 1.x compatibility harness)
```

`scripts/gate.sh --fix` runs `cargo fmt --all` first. `scripts/run.sh` starts the app on a sample folder.

### Standard milestone gate (`M<n>.G`)

1. `scripts/gate.sh` all PASS on the merged `main` (run on a branch `m<n>/gate` cut from it).
2. Every PARITY row of the milestone (the **M** column) has at least one named test or a line in the manual
   checklist of the milestone file.
3. Visual review where the milestone built UI: a Slint capture per new screen and theme in `docs/visual/`
   (`<screen>-<theme>-slint.png`, beside the 1.x picture `reference/z-work-tracker/docs/images/<name>.png` copied
   as `<screen>-<theme>-tauri.png`), reviewed in a new `## M<n>` section of docs/visual/REVIEW.md; pass = no medium
   or high defect.
4. Measurements where PLAN §10 asks (named per milestone), in a new section of docs/MEASUREMENTS.md; Mac numbers
   are provisional, Windows numbers stay "pending owner" until M8.
5. docs/MILESTONES.md gets an entry (create the file on first use): date, merge commit, PARITY rows delivered,
   tests added, gate result, visual verdict, measurements, open items carried on.
6. README.md updated where user-visible behaviour changed; then one milestone commit; the owner merges `--no-ff`.

## 2. Glossary (plain words)

| Term | Meaning |
|---|---|
| crate | One Rust package (a library or a program) with its own `Cargo.toml`. This repo has four in `crates/`. |
| workspace | The set of crates built together, listed in the root `Cargo.toml`; one `Cargo.lock` for all. |
| `cargo test` | Builds and runs the tests. `cargo test -p zwt-ui-logic rate_text` runs only the tests whose name contains `rate_text` in that crate. |
| `cargo clippy` | The Rust linter. This repo turns its warnings into errors (`-D warnings`). |
| `cargo fmt` | Formats the code; the gate only checks, `scripts/gate.sh --fix` formats. |
| `.slint` file | The UI, in Slint's own language (`crates/zwt-app/ui/`): components, properties, callbacks. Compiled into Rust by `build.rs`. |
| z-work-core | The 1.x app's engine (store, sync, billing, analytics), copied here unchanged (`crates/z-work-core`). |
| bridge | `crates/zwt-bridge`: the worker thread that owns the core's `Service`, takes commands, and turns changes into views for the UI. |
| topic | A named kind of change (projects, tasks, the shown day...). Each screen redraws only for its topics. |
| ui-logic | `crates/zwt-ui-logic`: small, pure functions ported from the 1.x TypeScript (formatting, colours, ordering). The friendliest place to write Rust. |
| testing backend | Slint's headless test mode: tests open windows in memory, click by accessible label and take screenshots without a screen. |
| windows-gnu build | The Windows `.exe`, built on the Mac with the MinGW toolchain (`--target x86_64-pc-windows-gnu`). |
| branch, merge `--no-ff` | Each task is a branch; `--no-ff` keeps a merge commit, so each task stays one visible step in history and can be reverted as one. |
| PARITY row | One line of docs/PARITY.md: a 1.x feature or rule 2.0 must match; tasks cite rows by number. |

## 3. Rust in this repo (one page)

**Layout.** `crates/z-work-core` (the engine, do not edit unless a task says so) -> `crates/zwt-bridge` (worker,
commands, views, topics) -> `crates/zwt-ui-logic` (pure helpers, no Slint) -> `crates/zwt-app` (the program:
`src/ui.rs` wires Slint to the bridge, `src/convert.rs` turns views into Slint rows, `ui/*.slint` draws).

**How a value flows.** A click in Slint calls a callback (`crates/zwt-app/ui/state.slint:174`
`callback start-task(string)`) -> `src/ui.rs:202` sends `Command::Start(id)` -> the worker
(`crates/zwt-bridge/src/worker.rs:112`) calls the core, sees what changed and sets topic bits -> the hub rebuilds only
those views (`views.rs:138` `TaskRow`) -> `src/convert.rs:69` `task_row` makes the Slint row -> the property updates
-> Slint redraws.

**Errors.** No `unwrap()`, `expect()`, `panic!` or `slice[i]` outside tests: clippy refuses them, because a crash in a
time tracker loses the user's running time. Use `Option` / `Result`, `?` to pass an error up
(`crates/zwt-bridge/src/datadir.rs:536`), `.get(i)` instead of `[i]`, and `match` or `if let` to handle the cases.

**Run one test.** `cargo test -p zwt-ui-logic --test logic rate_text` (crate, test file group, name filter).
Add `-- --nocapture` to see `println!` output.

**Read an error.** Look at the first `error[E....]` only; the `-->` line gives file:line:column; the `help:` line
is usually the fix. `rustc --explain E0502` explains a code. For clippy, the lint name (`clippy::indexing_slicing`)
is a link: search "clippy indexing_slicing" for the explanation.

**The five patterns you will see most.**

| Pattern | Example | Concepts |
|---|---|---|
| A pure function returning `Option` | `crates/zwt-ui-logic/src/color.rs:20` `normalize_hex` | [opt] [str] [iter] |
| A small formatter with `format!` | `crates/zwt-ui-logic/src/format.rs:13` `hours_minutes`, `:28` `percent_label` | [fn] |
| An enum and `match` | `crates/zwt-bridge/src/views.rs:74-105` `TaskGroup::of`, `index` | [enum] [match] |
| A `Result` passed up with `?` | `crates/zwt-bridge/src/datadir.rs:536` `given` | [err] |
| A test that ports a 1.x test | `crates/zwt-ui-logic/tests/logic/format.rs:16`; new files are added as `mod x;` in `tests/logic/main.rs` | [test] |

## 6. When a session gets stuck

Follow-up prompts to paste as they are:

| Situation | Paste |
|---|---|
| Gates red | "Run scripts/gate.sh and fix only what fails; change nothing else. Show me which gate failed and why, in plain words." |
| You lost track | "Explain in plain words what you changed so far and why, file by file, and what is left." |
| Too big | "Stop. Commit what works on this branch as WIP. Propose a split of the rest of this task into two tasks with their own subtasks and checks, as text I can paste into docs/roadmap/M<n>.md." |
| Gone wrong | "Stop. Show me `git status` and `git log --oneline main..HEAD`. Then reset this branch to main (`git reset --hard main`) only after I say yes." |
| My code does not compile | "Here is the error. Explain the first error in plain words, point at the line, and give me hint 1 only." |
| Unsure it is right | "Write one more test that would fail if this were wrong, run it, and tell me what it proves." |

Stop and ask for help (the owner decides, or a stronger session reviews) when: the same gate fails twice after
fixes; a test of the core (`crates/z-work-core`) fails; the session wants to edit the core, `theme.slint`, PARITY.md
or `Cargo.lock` versions without the task saying so; anything touches real data outside a temp or sample folder;
or the task has run past 1.5x its size.
